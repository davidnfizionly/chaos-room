# Architecture Decision Records

One line per decision that goes beyond `docs/PROJECT_PLAN.md`: what, why, what was rejected.

| # | Status | Decision | Why | Rejected |
| --- | --- | --- | --- | --- |
| 001 | Accepted | Terraform state locking uses the S3 native lockfile (`use_lockfile = true`, Terraform >= 1.10) instead of a DynamoDB lock table | Same locking guarantee with one fewer resource to create, secure and tear down; DynamoDB-based locking is deprecated in Terraform's S3 backend | DynamoDB lock table (listed in the plan, now deprecated by HashiCorp) |
| 002 | Accepted | Budget alert excludes credits and refunds (`include_credit = false`) | With promotional credits absorbing spend, a credit-inclusive budget reports ~0 USD and would never fire | Default cost types (credits included) |
| 003 | Accepted | The bootstrap stack (`infra/backend`) keeps its own state locally, gitignored | Avoids the chicken-and-egg of storing the state bucket's state in itself; only 7 small resources | Migrating bootstrap state into the bucket it creates |
| 004 | Accepted | Baseline telemetry comes from a local Node.js process acting as 3 registered IoT things over MQTT/mTLS; the "Lambda-driven" sabotage trigger is a Lambda (behind the dashboard API, Phase 4) that publishes a command to the device's command topic | Exercises the real device registration path (thing + X.509 cert + scoped policy), publishes every second, and costs nothing when stopped | A scheduled Lambda publisher (EventBridge's minimum rate is 1 minute, so no continuous stream, and it bypasses device registration) |
| 005 | Accepted | Device certificates are signed from locally generated CSRs (EC P-256) | Private keys never leave the machine and never enter Terraform state | `aws_iot_certificate` without CSR (AWS generates the key and Terraform stores it in state) |
| 006 | Accepted | One IoT policy for all devices, scoped with policy variables (`ThingName`, `Attributes[component]`) | Each device can only connect as itself, publish its own telemetry and receive its own commands, with a single policy to maintain | One policy per device; wildcard `iot:*` |
| 007 | Accepted | Second DynamoDB table `chaos-room-state` for per-component incident locks and failure-injection flags, separate from the append-only incident log | Keeps the audit log strictly append-only (PutItem with `attribute_not_exists` only, no Update/Delete granted anywhere) while mutable state lives elsewhere | Lock items inside the log table (would require UpdateItem/DeleteItem on the audit log) |
| 008 | Accepted (revised) | Dedup of repeated fault telemetry with a conditional lock per component: a reading opens an incident only if no lock exists or its broker ingest time is after the previous incident's settle window (`reopen_after` = remediation done + 1.5 s) | The device keeps publishing faulty readings every second until the fix reaches it; readings already in flight during the ~300 ms device round trip must not open a second incident. A fault that persists past the window is still caught on the next 1 s reading | Releasing the lock at remediation time (first version, produced a duplicate incident per run, see DEVLOG); dedup inside a Lambda |
| 009 | Accepted | Workflows write the incident log with the Step Functions direct DynamoDB integration; Lambdas only perform actions | No extra Lambda hop on the latency path; actions and audit stay separate | A logging Lambda |
| 010 | Accepted | The escalation scenario is injected with a DynamoDB flag (`INJECT#<component>.actuator_stuck`) read by the action Lambda, which then reports the actuator's failure | Deterministic, testable from the CLI and from the dashboard, no change to the workflow under test | Randomized failures; a separate "broken" workflow |
| 011 | Accepted | Headline latency is measured on the device's own clock: first faulty reading published -> remediation command received. AWS-side stage timings (ingest -> each step) are recorded from AWS clocks | Local and AWS clocks only agree to about a second, so a cross-clock difference would not be a trustworthy millisecond figure | Subtracting the device timestamp from AWS timestamps |
| 012 | Accepted | Step Functions log delivery permissions use `Resource: "*"` | AWS does not support resource-level permissions for the `logs:*LogDelivery` actions Step Functions requires; this is the only wildcard resource in the stack | None possible |
| 013 | Accepted | Dashboard data path: API Gateway HTTP API + 2 Lambdas (`GET /state` read-only, `POST /sabotage` and `POST /reset` for commands), polled every second | Simplest path that works locally with `npm run dev`; separate Lambdas keep read and write permissions apart | AppSync/WebSockets (more moving parts for a half-day UI); direct DynamoDB access from the browser (needs browser credentials) |
| 014 | Accepted | Latest telemetry per component is mirrored into `chaos-room-state` (`LIVE#<component>`) by a third IoT rule (`dynamoDBv2` PutItem) | The dashboard tiles need live values; the rule engine writes them with no extra code, ~3 writes/s on-demand while the simulator runs | Device Shadows (device code and policy changes); reading the MQTT stream from the browser |
| 015 | Accepted | API key enforced in the Lambdas (`x-api-key`, constant-time compare) on every route; the Vite dev proxy adds it server-side from gitignored `.env.local`, so it never reaches the browser; throttling 10 req/s; API removed at cleanup | HTTP APIs have no native API keys; this meets the "at least an API key" rule with no extra service | REST API + usage plan (more resources for the same protection); Lambda authorizer (extra hop on every 1 s poll) |
